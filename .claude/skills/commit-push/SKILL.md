# 커밋·푸시

본 스킬은 변경 사항을 커밋하고 원격에 push한다. 계획 문서나 런북(`docs/*`)이
있어도 참고용으로만 보고, 실제로 무엇이 바뀌었는지는 `git diff`로 직접 확인한다.

## Phase 1: 변경 사항 파악

1. `git branch --show-current`로 현재 브랜치를 확인하라. 브랜치명(`{type}/{이슈번호}-{slug}`)에서 이슈 번호를 추출하라.
   - 번호를 못 뽑으면 사용자에게 물어보라. 끝내 없으면 커밋 메시지의 `(#이슈번호)`는 생략한다.
2. 현재 브랜치가 `main`이면 "main에는 직접 커밋하지 않는다"를 알리고 중단하라.
   (이 저장소는 `dev` 없이 `feature → main`으로 간다. `.claude/spec/git-convention.md` 참조.)
3. `git status --short`로 스테이징·미스테이징·untracked 상태를 파악하라.
4. `git diff`(미스테이징)와 `git diff --staged`로 실제 변경 내용을 직접 확인하라.
   - untracked 파일은 diff에 잡히지 않는다. `git status`에 뜬 새 파일은 Read로 내용을 확인하라.
   - 커밋에 섞이면 안 되는 것이 untracked에 있으면 사용자에게 알리고 `.gitignore` 처리를 제안하라.
     임의로 커밋하지 마라. 이 저장소의 대표적 위험물: `tfplan`·`*.tfplan`(생성된 plan),
     `*.tfstate`(상태 파일), `.terraform/`(프로바이더 캐시), `*.tfvars`(비밀값 가능성).
5. 커밋할 변경이 없으면 그 사실을 알리고 중단하라.

> Skip 조건: 없음 (필수 Phase)

## Phase 2: 커밋 그룹핑 & 메시지 초안

1. `.claude/spec/git-convention.md`의 커밋 타입 표를 Read로 확인하라.
2. 변경 파일을 작업 성격별로 묶어라. 성격이 하나면 단일 커밋, 여러 갈래(예: 리소스 변경 + 런북 갱신)면 타입별로 분리하고,
   어느 파일이 어느 커밋에 들어가는지(스테이징 계획)를 정하라.
   - 모듈 정의와 그 모듈을 쓰는 루트 스택 배선이 한 변경의 앞뒷면이면 굳이 쪼개지 마라.
     쪼개는 기준은 파일 위치(root vs `modules/` vs `dns/`)가 아니라 작업의 성격이다.
3. 그룹마다 커밋 메시지 초안을 작성하라. 제목 한 줄 + 빈 줄 + body 구조다.

   **제목**: `{type}: 내용(#{이슈번호})` — 한 줄 명사형 한국어 (예: `feat: RDS 자동 백업 설정 추가(#12)`).

   **body**: `- ` 항목 1~3개. **항목 하나는 한 줄**로 끝낸다. 산문 문단으로 늘여 쓰지 마라.
   - 각 항목은 `{무엇이 문제였는지} → {그래서 무엇을 했는지}` 한 줄이다.
     제목이 "무엇을"이면 body는 "왜"다. 바꾼 파일을 나열하지 마라 — 그건 diff가 이미 말해준다.
   - 갈래가 여럿일 때만 항목을 늘려라. 한 줄로 끝나면 한 줄만 쓴다. 없는 얘기를 지어내 채우지 마라.
   - 자명한 변경(오타 수정, 포맷팅, 프로바이더 버전 올리기 등)은 body를 생략한다.
     쓸 말이 없는데 억지로 쓴 body는 안 쓴 것보다 나쁘다.
   - 한 줄에 안 담기는 배경(재현 경로, 대안을 버린 이유, 긴 원인 분석)은 body에 넣지 마라.
     그런 내용은 사용자가 따로 wiki에 정리한다. 커밋 메시지에서 링크나 문서를 가리키려 하지 마라.
   - 예:
     ```
     fix: ALB 헬스체크 경로 불일치 수정(#12)

     - 헬스체크가 404로 실패해 타겟이 계속 draining되는 문제가 있어 경로를 서버의 /actuator/health로 정정
     ```

## Phase 3: 사용자 확인

1. 커밋 그룹·메시지 초안(제목과 body 전문)·푸시 대상(브랜치, 첫 푸시 여부)을 사용자에게 제시하고
   "이렇게 커밋·푸시할까요?"로 확인받아라. body는 요약하지 말고 커밋에 들어갈 문장 그대로 보여줘라 —
   사용자가 고칠 곳을 짚으려면 실제 문장을 봐야 한다.
2. 수정 요청이 있으면 반영 후 다시 확인하라. 사용자가 승인하기 전까지 커밋·푸시하지 마라.

> 다음 Phase 조건: 사용자가 승인했을 때

> Skip 조건: 없음 (필수 Phase)

## Phase 4: 커밋 & 푸시

1. 그룹별로 해당 파일만 스테이징하라 (`git add {파일들}`). `git add -A`처럼 한 번에 담지 마라 —
   그룹핑이 무의미해진다.
2. 메시지를 스크래치 파일에 Write한 뒤 `git commit -F {메시지파일}`로 커밋하라. 그룹이 여러 개면 반복한다.
   - 파일 형태: 제목 한 줄, 빈 줄, body. `-m`을 여러 번 쓰는 방식은 백틱·따옴표·줄바꿈이 섞인 body를
     셸이 깨먹을 수 있으니 쓰지 마라.
   - body가 없는 커밋(자명한 변경)은 `git commit -m "{제목}"`으로 끝내도 된다.
   ```
   {type}: 내용(#{이슈번호})

   왜 이렇게 했는지. 어떤 문제를 풀려던 것인지.
   ```
3. upstream 상태를 판별해 push하라:
   ```bash
   git rev-parse --abbrev-ref --symbolic-full-name @{u} 2>/dev/null
   ```
   - 출력이 없거나(첫 푸시) `origin/{현재브랜치}`와 다르면 `git push -u origin HEAD`
     (원격 반영 + upstream을 동일명 원격 브랜치로 설정)
   - 출력이 `origin/{현재브랜치}`와 일치하면 `git push`
   - push가 거부되면(원격이 앞서 있음) 사용자에게 알리고 중단하라. 강제 푸시(`--force`)는 하지 마라.
