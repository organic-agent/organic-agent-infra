# 이슈·PR 본문 쓰는 법

이슈·PR 본문을 쓸 때 따른다 — `gh issue create`·`gh pr create`로 직접 만들 때도 같다. 섹션 이름은 저장소 템플릿
(`.github/ISSUE_TEMPLATE/issue-template.md`, `.github/pull_request_template.md`)이 정하고, 이 문서는 **그 안을 어떻게 채우는지**를 정한다.
제목·브랜치·라벨 형식은 `git-convention.md`가 정한다. `organic-agent-server`·`organic-agent-ai`의 `issue-pr-writing.md`와 같은 규칙이고,
이 저장소에만 있는 것은 PR의 **Plan 결과 / 롤백** 섹션이다.

목표: 처음 보는 팀원이 **10초 안에 "무엇이 왜 바뀌나"**를 알고, 1분 안에 리뷰할 곳을 찾는다.
이 저장소는 머지가 곧 apply라, 리뷰어가 "머지하면 운영에서 무엇이 바뀌나"까지 본문만으로 알 수 있어야 한다.

## 다섯 가지 규칙

1. **맨 위에 한 줄 요약.** 템플릿 첫 섹션 바로 위에 `> ` 인용 한 줄로 쓴다. "무엇을 → 왜"를 한 문장에.
   - 좋음: `> Bedrock 호출을 미국 리전으로 돌려, 조직 정책에 막힌 그룹 이름 짓기와 추천을 다시 살린다.`
   - 나쁨: `> fix: bedrock_model_id global → us, VPC peering 추가 (#71)`
2. **세 질문으로 나눈다.** 왜(문제) / 무엇을(바꾼 것) / 어떻게 확인(검증). 한 덩어리에 섞지 않는다.
3. **한 줄에 한 사실.** 괄호 안에 또 설명을 넣지 않는다. 문장이 쉼표 두 개를 넘으면 두 줄로 나눈다.
4. **바뀐 리소스·값·경로는 표로.** `전 → 후` 두 열 표가 문단보다 빠르다. 행은 7개 이하, 넘으면 묶음별로 나눈다.
5. **처음 보는 말은 풀어 쓴다.** 내부 약어(SCP, PHZ, PR-3c, 결정 K)는 처음 나올 때 한 번 풀이한다.
   풀이가 길면 그 말을 쓰지 않는다.

## 모양

- **주의 사항은 맨 위에 하나만.** 머지 순서·수동 작업·다운타임처럼 놓치면 사고가 나는 것만 GitHub 알림으로 쓴다.
  ```markdown
  > [!WARNING]
  > 머지 뒤 앱을 재시작해야 한다. 재시작 전까지 앱은 옛 모델 ID로 호출해 계속 실패한다.
  ```
  경고는 두 줄 안. 이유가 더 필요하면 본문에서 풀고, 경고에는 "무엇을 해야 하는지·하면 안 되는지"만 둔다.
- **칸 제목은 `###`, 묶음 제목은 굵은 글씨.** 왜·무엇을·확인 같은 칸은 `###` 소제목으로, 칸 안의 변경 묶음은 `1. **네트워크 경로**`처럼 굵은 글씨로.
- **변경은 묶음 3~5개로.** 커밋 목록이나 plan의 리소스 목록을 옮기지 않는다. 묶음마다 굵은 제목 한 줄 + 항목 3개 이하.
- **경로가 바뀌면 그림 하나.** 네트워크 경로·호출 순서·권한 흐름이 바뀔 때만 작은 Mermaid(노드 6개 이하)를 넣는다.
  값만 바뀐 변경에는 그리지 않는다.
- **길면 접는다.** 본문이 화면 한 장(약 40줄)을 넘으면 세부 목록·리소스 목록은 `<details><summary>자세히</summary>…</details>`로 접는다.
  요약·경고·Plan 요약·롤백은 접지 않는다.
- **리소스 주소·변수 이름은 백틱, 파일 경로는 꼭 필요할 때만.** 리뷰어가 열어 봐야 하는 파일만 경로를 쓴다.
- **plan 출력 전문을 붙이지 않는다.** PR마다 CI가 plan 코멘트를 단다. 본문에는 리뷰어가 봐야 할 변경만 추린다.

## 제목

`git-convention.md`의 형식 `{type}: {설명}(#이슈번호)`에서 **설명은 결과를 말하는 한국어 한 구절**로 쓴다.
- 좋음: `fix: Bedrock 호출을 미국 리전 경로로 우회`
- 나쁨: `fix: global. → us. 프로필, aws_vpc_peering_connection + PHZ 추가`

## 이슈 채우기

| 템플릿 섹션 | 무엇을 쓰나 |
|---|---|
| (맨 위) | 한 줄 요약 `>` |
| 1. Issue Description | **왜** — 지금 무엇이 불편하거나 틀렸는지 2~4줄. 해결책은 여기 쓰지 않는다 |
| 2. Issue Task | **무엇을** — 체크박스 3~7개. 하나가 "끝났다"고 말할 수 있는 크기로 |
| 3. Related Stack/Module | 해당하는 것만 `- [x]` |

이슈에는 구현 방법을 길게 쓰지 않는다. "어떻게"는 PR의 몫이다.

## PR 채우기

| 템플릿 섹션 | 무엇을 쓰나 |
|---|---|
| (맨 위) | 한 줄 요약 `>` + 필요할 때만 경고 하나 |
| 1. 연관 이슈 | `- close #N` |
| 2. 구현 사항 | 왜 / 무엇을 바꿨나 / 어떻게 확인했나 — 이 순서로 세 칸 |
| 3. Plan 결과 / 롤백 | Plan 요약 / 주의할 변경 / 롤백 — 이 순서로 세 칸 |

제목은 세 층이다 — **템플릿 섹션 `##` → 칸 `###` → 본문**.
- 템플릿 섹션("1. 연관 이슈", "2. 구현 사항", "3. Plan 결과 / 롤백", 이슈의 세 섹션)은 `##`. GitHub이 `##` 아래에 밑줄을 그으므로 `---`를 따로 넣지 않는다.
- 칸(왜·무엇을·확인, Plan 요약·주의할 변경·롤백)은 `###`.
- `####`와 굵은 글씨는 GitHub에서 본문과 같은 크기라 칸 제목으로 쓰지 않는다. 굵은 글씨는 칸 안의 묶음 제목에만.

```markdown
## 2. 구현 사항

### 왜
- 문제 한두 줄

### 무엇을 바꿨나
| 전 | 후 |
|---|---|
| … | … |

### 어떻게 확인했나
- 정적 검사: `fmt`·`validate`·정적 테스트 몇 개 통과
- 직접 확인: (했으면) 무엇을 봤는지

## 3. Plan 결과 / 롤백

### Plan 요약
- `N to add, N to change, N to destroy` — 교체(replace) N개

### 주의할 변경
- 교체·삭제·권한 변경·예상 다운타임. 없으면 "없음" 한 줄

### 롤백
- 되돌리는 방법 한두 줄. revert로 안 돌아오는 것(데이터 삭제, 수동 주입 값)이 있으면 여기 적는다
```

- **주의할 변경**에는 plan에서 사람이 놀랄 만한 것만 쓴다 — 교체되는 EC2·RDS·Lambda, 지워지는 리소스, 넓어지거나 좁아지는 IAM,
  끊기는 시간. 태그·설명 같은 무해한 제자리 변경은 쓰지 않는다.
- apply 뒤에 사람이 해야 하는 일(재시작, 값 주입, 다른 저장소 배포)은 **주의할 변경**에 쓰고, 놓치면 사고가 나면 맨 위 경고로도 올린다.
- 아직 확인하지 못한 것은 확인한 것처럼 쓰지 않는다. "apply 뒤에 확인 필요"라고 적는다.
- 리소스가 바뀌지 않는 PR(문서·스킬·테스트만)이면 3번 섹션은 "리소스 변경 없음" 한 줄로 끝낸다.

## 예시

나쁨 — 한 항목에 여러 사실, 괄호 속 설명, 풀지 않은 약어:

```markdown
- 추가: us-east-1 VPC(10.1.0.0/24, IGW·NAT 없음) + bedrock-runtime VPCE + peering + PHZ(private DNS off라 서울 VPC에서 alias로 풂),
  SG는 cross-region이라 CIDR, 서울 VPCE·SG·`interface_endpoint_subnet_indexes` 삭제.
```

좋음:

```markdown
> Bedrock 호출을 미국 리전으로 돌려, 조직 정책에 막힌 그룹 이름 짓기와 추천을 다시 살린다.

> [!WARNING]
> 머지 뒤 앱을 재시작해야 한다. 재시작 전까지 앱은 옛 모델 ID로 호출해 계속 실패한다.

## 1. 연관 이슈

- close #71

## 2. 구현 사항

### 왜
- 조직 정책이 9월 30일부터 `global.` 모델 프로필 호출을 거부한다.
- `us.` 프로필은 통과하지만 미국 리전에서만 부를 수 있다.
- 이름 짓기 Lambda는 인터넷이 없는 서브넷에 있어 미국 리전에 닿지 못한다.

### 무엇을 바꿨나
| 전 | 후 |
|---|---|
| 모델 `global.anthropic.claude-sonnet-4-6` | `us.anthropic.claude-sonnet-4-6` |
| 호출 리전 서울 | 미국 버지니아(`us-east-1`) |
| 서울의 Bedrock 전용 엔드포인트 | 미국 리전의 엔드포인트 + 리전 간 VPC 연결 |

### 어떻게 확인했나
- 정적 검사: `fmt`·`validate`·정적 테스트 10개 통과
- 직접 확인: 미국 리전에 `us.` 프로필로 호출해 성공, `global.`은 거부됨

## 3. Plan 결과 / 롤백

### Plan 요약
- `15 to add, 5 to change, 3 to destroy` — 교체 없음

### 주의할 변경
- 삭제: 서울의 Bedrock 엔드포인트와 그 보안 그룹. 지금은 호출이 막혀 있어 추가 다운타임이 없다.
- 권한: Lambda·앱 롤의 호출 대상이 `us.` 프로필로 바뀐다.
- apply 뒤 앱 재시작이 필요하다. Lambda·앱의 실제 호출은 apply 뒤에 확인해야 한다.

### 롤백
- 이 PR을 revert해 apply한다. 다만 `global.` 프로필은 정책이 풀리기 전까지 계속 막혀 있다.
```

## 만들기 전 자가 점검

본문을 다 쓰면 아래를 하나씩 확인하고, 걸리면 고친 뒤 **초안을 사용자에게 보여 주고 확인받은 다음** 만든다.

- [ ] 맨 위 한 줄만 읽고 무엇이 왜 바뀌는지 알 수 있다
- [ ] 제목이 세 층이다: 템플릿 섹션 `##` → 칸 `###` → 본문 (`####`·굵은 글씨는 본문과 크기가 같다)
- [ ] 한 줄에 사실이 하나다 (괄호 속 괄호, 쉼표 셋 이상 없음)
- [ ] 리소스·값·경로 변경이 표로 정리돼 있다
- [ ] 내부 약어가 풀이 없이 나오지 않는다
- [ ] 경고는 정말 사고를 막는 것 하나뿐이다
- [ ] 화면 한 장을 넘는 부분은 접혀 있다
- [ ] (PR) plan 개수와 교체·삭제·권한 변경이 적혀 있고, 확인하지 못한 것은 그렇다고 적혀 있다
- [ ] (PR) 롤백 방법과 revert로 돌아오지 않는 것이 적혀 있다
